# 糖尿病视网膜病变平台前端改造方案

> 这是团队的任务布置与协作说明。项目用于算法创新赛演示，不代表真实临床系统、真实患者数据或临床验证结果。

## 项目目标

以现有 Vue 2 / Element UI 前端为基础，改造成糖尿病视网膜病变（DR）筛查与随访平台的比赛演示版。

核心流程：

```text
选择患者 → 确认右眼/左眼 → 采集或选择眼底图 → 质控
→ 展示研究模型草稿或转人工状态 → 医生审核签发
→ 创建转诊/复查任务 → 患者查看已签发报告
```

平台服务四类演示角色：患者、基层筛查人员、眼科医生和区域管理人员。它是 DR 专项平台，不扩展为泛化的血糖、饮食或运动管理应用。

## 页面规划

| 页面 | 主要内容 |
| --- | --- |
| 工作台 | 按演示角色显示待采集、待审核和待随访任务 |
| 患者档案 | 演示患者编号、所属机构、左右眼检查记录和时间线 |
| 筛查采集 | 核对患者与眼别，选择眼底图，登记设备和检查时间 |
| 质控结果 | 显示通过、需重拍、不可判读、资料缺失等状态与原因 |
| 医生审核 | 查看图像和结构化证据，接受、修改或退回 AI 草稿并签发 |
| 报告详情 | 显示医生签发内容、眼别、时间、来源和版本 |
| 转诊与随访 | 显示待联系、已提醒、已预约、已完成、逾期等任务状态 |
| 患者服务页 | 仅查看已签发报告、已确认计划和提醒 |
| 区域看板 | 按机构汇总筛查、质控、待审核和随访进度 |

## 前端设计和数据约定

- 采用深青绿、蓝灰与浅色背景；风险和待办同时使用文字、图标与颜色表达。
- 每次检查按“患者—眼别—时间”组织，记录患者编号、检查编号、右眼/左眼、采集时间、机构、设备和数据来源。
- 分别表示资料缺失、影像低质、数据过期、设备未知和服务故障；不补造数据，不把左右眼合并成一个眼级结论。
- AI 草稿和医生签发结果必须清楚区分；签发后才进入患者服务与转诊/复查任务。
- 比赛版模型、质控与区域统计均使用明确标记的演示或研究数据，不冒充临床验证结果。
- 没有 OCT 时只能显示“未提供 / 未评估”，不能显示已确认 DME。
- 公开仓库不得放真实患者信息、真实眼底影像、账号、密钥或训练数据集。

## 三项实施任务

### 任务一：前端底座、主题、路由和共用数据

**要做的工作**

1. 清理乳腺癌标题、菜单、图片、演示数据和业务路由，保留 Vue / Element UI 后台外壳与通用组件。
2. 更新产品名称、登录后首页、主题变量和导航。
3. 建立工作台、患者档案、筛查采集、医生审核、转诊随访、患者服务和区域看板的路由。
4. 统一患者、检查、眼别、影像、AI 草稿、签发报告和随访任务的演示数据结构。
5. 建立共用组件：患者信息栏、左右眼切换、图像预览、来源/设备标签、质控状态、审核记录、检查时间线和任务状态。
6. 创建集中管理的 DR 合成数据和 mock 服务，不把模拟数据继续写在页面组件里。

**主要改动位置**

- `src/settings.js`：产品名称和浏览器标题。
- `src/router/`：登录后首页、根路径和 DR 专用路由。
- `src/styles/variables.scss`：主题颜色。
- `src/components/dr/`：共用 DR 组件。
- `src/mock/dr/`：模拟病例与 mock 服务。
- `src/views/`：新业务页面骨架。

**完成标准**

新菜单可以进入所有规划页面；页面刷新和直接访问路由正常；统一模拟数据至少区分右眼、左眼及任务状态，供任务二、三复用。

### 任务二：筛查采集、质控和医生审核签发

**要做的工作**

1. 实现患者档案、检查列表和左右眼检查时间线。
2. 实现“确认患者 → 确认眼别 → 选择/导入眼底图 → 登记设备和时间 → 提交质控”的采集向导。
3. 展示质控通过、需重拍、严重不可判读、设备未知等结果，并说明原因和下一步。
4. 用合成或明确标记的研究数据展示病灶证据、ICDR 候选等级、可用/缺失模态和 AI 草稿状态。
5. 实现医生接受、修改、退回或签发；保留审核意见、修改原因、医生和签发时间。

**主要改动位置**

- `src/views/patients/`
- `src/views/screening/`
- `src/views/review/`
- `src/views/prediction/input/index.vue`：采集向导。
- `src/views/prediction/assess/index.vue`：质控结果和 AI 草稿。
- `src/views/prediction/subtype/index.vue`：眼别记录与影像证据。

**完成标准**

从患者档案可以走到采集、质控、医生审核和签发；至少演示通过、重拍、需复核和医生修改签发四种状态；未确认患者或眼别不能提交；缺少 OCT 时只能显示未提供 / 未评估；所有 AI 内容均有研究或演示标识。

### 任务三：签发报告、患者随访、区域看板及必要后端

**要做的工作**

1. 将签发报告与已确认的转诊/复查计划串联。
2. 实现转诊和随访状态流转：待联系、已提醒、已预约、已完成、逾期/失访。
3. 实现患者服务页，只显示已签发报告和已确认计划，并提供提醒确认/随访反馈。
4. 实现区域演示看板，统计筛查、质控和随访任务；数字必须与演示病例一致。
5. 串通“医生签发 → 建立任务 → 患者查看/确认 → 区域状态更新”。
6. 默认使用 mock 服务；只有跨设备持久化、多人登录、真实影像保存或跨机构审计确实需要时，再增加对应最小后端。

**主要改动位置**

- `src/views/advice/`：签发报告。
- `src/views/followup/`：转诊与随访。
- `src/views/patient/`：患者服务。
- `src/views/region/`：区域看板。
- `src/services/dr/`：mock/API 适配层。

**完成标准**

完整演示报告签发、任务创建、患者查看/确认和区域汇总；患者端看不到未签发内容；统计与同一批模拟数据一致。

## 演示与数据边界

- 内置 ResNet18 推理服务仅用于研究与竞赛演示，所有结果都必须经过医生复核。
- 病灶证据没有真实标注训练权重时，必须显示“演示草稿 / 未提供”，不能当作真实病灶检测。
- 不把内部实验指标表述为临床准确率、临床风险或治疗建议。
- 本仓库只保存运行所需的研究权重；训练数据集和真实医疗资料不得提交。

## 一键运行

建议安装 Node.js 20 LTS（当前也已验证 Node.js 24 可用）以及 Python 3.10 或更高版本。

在 Windows 资源管理器中双击：

```text
启动演示.cmd
```

或在项目根目录运行：

```powershell
powershell -ExecutionPolicy Bypass -File .\start-demo.ps1
```

首次运行会准备 Python 推理环境和前端依赖。登录演示账号：`admin` 或 `editor`；密码：`111111`。

```text

```

更多字段说明见 [DR 数据与服务约定](docs/dr-data-contract.md)。
