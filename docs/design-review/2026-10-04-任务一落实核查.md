## 需要优先补齐的内容

### 1. 三个规划入口没有落地

证据：src/router/index.js:28，src/router/modules/prediction.js:8。

| 规划入口 | 当前路由 | 状态 |
| --- | --- | --- |
| 工作台 | /dashboard | 已有 |
| 患者档案 | /personal/index | 已有 |
| 筛查采集 | /prediction/input | 已有 |
| 医生审核 | 无独立路由 | 缺失；多智能体共识和双眼证据为草稿展示页 |
| 转诊随访 | /advice/index | 已有处置与随访入口，正式转诊任务仍为占位 |
| 患者服务 | 无对应路由 | 缺失；眼健康助手提供流程问答，不能视为患者报告/计划服务页 |
| 区域看板 | 无对应路由 | 缺失；工作台图表不能替代按机构汇总的区域入口 |

现有其他入口为 /prediction/assess（多智能体共识）、/prediction/subtype（双眼分级与证据）和 /chat/index（眼健康助手）。虽然当前业务页面也有七个，但与任务要求的七类入口不相同。

任务一需要建立这些页面的路由与骨架；完整审核签发、患者确认和区域统计交互属于后续任务二、三，本次不以这些后续功能未完成为额外验收要求。

prediction.js 已替换旧菜单文案和页面内容。保留原兼容路径或文件名本身不构成验收失败；缺少规划入口才是实质问题。

### 2. 当前数据不足以作为任务二、三的统一输入

证据：src/data/retina-demo.js:4、19、41、57、61。

| 实体 | 当前状态 | 需要形成的共用约定 |
| --- | --- | --- |
| 患者 | 6 个固定患者，带病例编号、左右眼等级和流程状态 | 稳定 patientId，并与检查、报告和任务关联 |
| 检查 | 单个 intake 及患者上的 date | examinationId、patientId、检查时间、机构、逐眼资料 |
| 眼别 | rightGrade / leftGrade 和 rightCfp 等文件槽 | 统一 OD / OS 或明确的 right / left 枚举，贯穿检查、影像、草稿和报告 |
| 影像 | CFP / OCT 布尔值；当前本地文件的名称、大小、类型、预览 URL | imageId、examinationId、眼别、模态、来源、设备、采集时间和质控状态 |
| AI 草稿 | 页面依据患者字段拼接显示，缺少独立对象 | draftId、对应检查、逐眼候选结果、证据和草稿状态 |
| 签发报告 | 固定显示未签发，没有演示报告对象 | reportId、对应检查/草稿、逐眼结论、版本、签发人和签发时间 |
| 随访任务 | taskStates 字典和页面内的准备清单 | taskId、patientId、reportId、类型、到期时间、状态及更新记录 |

现有 taskStates 实际保存的是备注对象；setTaskState 的调用并未建立统一任务状态枚举。病例的“待复核”“待采集”等流程标签，也不能替代每条随访任务的状态。

数据更新也尚未共用同一个存储来源：档案编辑和 saveIntake 更新 demoState.patient，工作台读取的仍是独立的 patients 数组。任务二、三接入前应统一读取和更新接口，让工作台、检查、报告、任务及区域统计关联同一批对象。

任务一无需实现真实推理、真实签发或跨设备持久化，但需要提供明确标记的合成对象和服务约定，让后续任务复用同一批检查、报告和任务数据。

## 补齐顺序

1. 固定七类实体、左右眼及任务状态的约定，集中合成数据并建立 DR mock 服务。
2. 补医生审核、患者服务、区域看板路由与页面骨架；在路由中关联患者和检查标识。
3. 整理现有患者栏及影像查看组件，补来源/设备、质控、审核记录、时间线和任务状态组件。
4. 将页面内的检查记录、草稿和任务迁入共用数据服务，清理旧业务图片并更新实施说明。
5. 用同一批合成病例检查全部规划入口、直达/刷新和跨页数据关联，再验收任务一。
